# v2.3.0 公開前後の検証計画（#5546）

対象：Redmine #5546「v2.3.0 の公開前後の検証計画を設計する」（親 #5542、v2.3.0 の Phase 1）。基準は `230_ロードマップ` version 1。

本書は、D03（導入から実行への引き継ぎ）と D05（実行対象と保存用 Python）の候補ごとに、公開前に何を追跡し、公開版で何を直接確認するかを比べるための計画案である。#5547 が方式と検証方法を一緒に選べるように、候補ごとの確認量を具体的な数で示す。

本書は次のどれでもない。D01〜D08 の採用、D08（公開後検証）の確定、新しい公開パラメーターの名称・型・既定値の決定、CI の実行や合格、公開。job 名・件数・判定処理の具体的な整備は Phase 4・6 が行う。本書の作成では、CI・実測・Redmine の変更を行っていない。

本書の「D08」は、v2.3.0 ロードマップの D08（公開後検証）を指す。v2.2.0 の資産にも D08・D09 という名前があり、意味が異なる。混同を避けるため、v2.2.0 のものには必ず「v2.2.0 の」を付ける。

| v2.2.0 の D09 案 (a) | 失敗処理が端末判定・`BASH_ENV`・CircleCI 固有の環境・Orb 外のファイルに依存しないことを前提に、非 0 の経路を公開前の確認と公開物の同一性で追跡する方式（`RELEASE_V2_2_0.md` 1章） |

### 0.2 経路

| 記号 | 経路 | 本書での扱い |
| --- | --- | --- |
| R0 | 既存経路。install は `python -m pip`、execute は PATH 上の `yamllint`、保存は PATH 上の `python3 -I` | 追加指定をしない利用。どの候補でも動作を変えない |
| R0e | 既存の execute 単独利用。利用者が PATH に用意した yamllint で execute だけを呼ぶ | 親 #5542 の境界「install を必須化しない」。基準の CI には install を使わない job がない（§2.3） |
| R1 | 仮想環境を作らない Python 選択。選んだ Python へ導入し、その Python に対応する yamllint を使う | H2 の判断待ち（採用しない／必須／条件付き） |
| R2 | 別仮想環境への導入。基になる Python から別の venv を用意し、そこへ導入して実行する | 管理標識のある基底環境から別 venv へ導入する形を含む（D06 の必須候補） |
| R3 | 導入済み環境で execute だけを使う。利用者が用意した環境を execute に指定し、Orb の install を使わない | 成立する形が D03 の候補で変わる（§3.4） |

### 0.3 候補の記号

| 記号 | 内容 | 出どころ |
| --- | --- | --- |
| X1 | 明示方式のうち「指定の重複」。install と execute の呼び出しごとに同じ環境を指定し、step 間で状態を持ち越さない | ロードマップ D03 |
| X2 | 明示方式のうち「受け渡し」。install が記録した導入先を、後の step の execute が読む | ロードマップ D03。M2 の明示方式の観測はこの形（M2 §5、§18.2） |
| B | BASH_ENV 方式。install が `BASH_ENV` に追記し、後続 step の PATH を変える | M2 §6、§18.2 |
| P | 保存補助処理は PATH 上の `python3 -I` を使い続ける | ロードマップ D05 の比較表 |
| S | 保存補助処理は選択した環境の Python を使う | 同上 |
| H2=N／Y／C | R1 を採用しない／必須に含める／条件付きで含める | ロードマップ H2 |

X1・X2 は、明示方式の中で検証量が変わる二つの形を区別するための記号である。新しい API 案でも採否でもない。B は、M2 で観測した「venv の bin を PATH の先頭に追記する」形を指す。PATH を変えない別の形を検討する場合は、§10 の手順で比較を補う。P と S が同じ Python を指すかどうかは、D03 の候補ではなく、各 step で `python3` として実際に解決される Python で決まる（§3.3）。X1 は前の指定を保持しないため、execute が知るのは自分に渡された指定だけである（§4.3）。

### 0.4 証拠の水準

| 記号 | 水準 | 示せること | 示せないこと |
| --- | --- | --- | --- |
| L1 | 子プロセス | 実スクリプトを制御した入力で動かしたときの終了値・stdout・stderr・ファイル | step の境界、CircleCI 上の step の状態 |
| L2 | 実 Orb step | source CI（inline Orb）での実際の install・execute step の動作 | 非 0 で終わる step（成功必須の job に置けない） |
| L3 | 実 CircleCI の別 run step | install と execute、その間の利用者 step をまたいだ参照先と副作用 | 公開版での動作 |
| L4 | 制御した故障 | 誤った実装や壊れた観測を、検査が不合格にできること（判定能力） | 実際の故障の起きやすさ |

本書の「公開前の追跡」は、同じリリース候補（RC）で行う L1〜L4 と、RC・タグ・公開物の全内容比較を合わせたものを指す。「公開後の直接確認」は L5 を指す。

#5544・#5545 の実測は、基準スクリプトと実験設定による設計の根拠である。L1〜L5 のどれでもなく、製品の合格証拠には使わない。

### 2.3 固定値を更新するときの決まり

`compatibility-contract.json` の hash や版を更新するときは、何の保証を維持する更新かを対応付ける（ロードマップ「検証契約と公開条件を維持する」）。

- `src/scripts/execute.sh` などを変えたときは、hash の更新と同時に、影響する suite と実 step を同じ RC で通す。
- 元の11件の本体を変えないなら、`legacy_job_sha256` も変えない。
- job を追加するときは、pack の requires、検査器が期待する依存、故障対照の3つを同時に更新する。

基準の CI には、install を使わずに execute だけを呼ぶ job がない。`test-deploy.yml` で execute を呼ぶ job は、すべて先に install を呼ぶ。現在は execute が install の結果に依存しないので問題にならないが、X2 や B では execute が install の結果に依存し得る。そこで、R0e を確認する job を公開前・公開後の両方に加える案とする（§5.1 の K5、§5.5）。既存保証を弱めるものではなく、境界を守るための追加である。

### 4.3 既存の観測器と v2.2.0 の D09 案 (a) を流用しない条件

既存の観測器は、BASH_ENV を使って PATH の先頭に記録用の `yamllint` を置き、本体の位置で呼び出しを捕まえる（`verify-boolean-parameters.py`、`verify-output-file.py`、`targets-test` などの shim）。新しい経路では、この方法をそのまま使えない。

- X1・X2：execute が選択環境の yamllint を直接起動するなら、PATH 上の記録用 `yamllint` は呼ばれない。
- B：Orb 自身の BASH_ENV への追記と観測器の追記の順序によって、どちらが PATH の先頭になるかが変わる。

新しい経路の boolean・保存の観測は、M-a の起動記録など、新しい経路で実際に呼ばれる位置の手段で行う。既存経路の観測器は、R0 の確認にそのまま使う。

v2.2.0 の D09 案 (a) は、失敗処理が端末判定・BASH_ENV・CircleCI 固有の環境・Orb 外のファイルに依存しないことを前提としていた（`RELEASE_V2_2_0.md` 1章）。この前提が新しい経路でどこまで成り立つかを、候補ごとに分ける。

| D03 | 前提との関係 | 本計画の扱い |
| --- | --- | --- |
| X1 | step 間で持ち越す状態はないが、それだけでは前提は成り立たない。選択先は Orb 外のファイルで、install と execute に別々の有効な環境を指定すると、各 step は単独で成功し得る。X1 は前の指定を保持しないため、execute が知るのは自分に渡された指定だけである。M2 の `selection-*` は不在の絶対パスを指定した比較用の呼び出しで、Orb の診断の証拠ではない | 新しい経路の lint error（K2）は直接確認する。環境選択の失敗は、次の条件をすべて満たす場合に限り公開前の追跡に置く。(1) 同じ RC の実 step（L3）で、指定の伝達と実行先を確認する。install と異なる有効な指定を execute に渡したときに、execute の指定先が起動することも起動記録で確認する。(2) 指定先の不在に対する診断を、制御した試験（L1・L4）で確認する。(3) 異なる有効な指定は、各呼び出しの指定を優先する（X1 の定義のまま）。不一致を Orb が拒否する案には、比較元の指定を識別する仕組み（step 間の状態）が必要で、X1 の定義から外れる。その場合の契約と検証量は、X2 と同じ扱いで #5547 の比較に加える。満たせない場合は K7 を直接確認に戻す。X1 の K7 が直接確かめられるのは指定先の不在だけで、有効な指定どうしの不一致の証拠にはならない |
| X2 | execute が前の step の記録ファイルに依存する。前提が成り立たない | ③（K7）を直接確認する。②は、execute が追加経路の要求を識別できる契約の場合に、K9 として直接確認の候補にする |
| B | 失敗処理が BASH_ENV による PATH に依存する。前提が成り立たない（ロードマップ Phase 6） | ③（K7）と副作用（K6）を直接確認する。②は X2 と同じ扱い（K9） |

導入失敗（M-c）も同じ考え方で扱う。pip の失敗、途中まで作られた venv、失敗後の古い選択の再利用を別々の項目として判定し、公開前に判定できない項目は項目名を残す。公開後に移す場合は、対応するケースと件数を再計算する。K8 が代わりに確かめられるのは venv 作成の失敗だけである。
